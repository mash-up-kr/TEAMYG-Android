# docs 기록 구조 개선 설계 — 현재 상태·이력·기준선 분리

- 작성일: 2026-09-26
- 대상 브랜치: `feature/#525-ai-docs-set-up`
- 계기: `docs/index.md`·`docs/synthesis/lint-2026-07-06-parfait.md`에 대한 팀 리뷰
  ("코드로 유추 가능한 디테일을 다 남겨야 하나", "정합성 수정 내역까지 docs로 남겨야 하나")

## 1. 목적

`docs/`가 에이전트의 **재구성 비용을 줄이는** 문서가 되게 만든다.

지금 구조는 반대로 동작한다.

1. `docs/index.md`의 「지금 상태 (1줄)」 절이 284줄이고, 볼드 날짜 머리 항목이 37개다.
   현재 상태를 알려면 이력을 읽고 머릿속에서 합쳐야 한다.
2. 쌓기만 하고 고쳐 쓰지 않아 index 안에서 주장이 서로 모순된다. 예: 2026-08-17 항목은
   "다섯 갈래 중 넷(남은 하나는 배경 변경)", "저장은 아직 로그 한 줄"이라 적고, 같은 문서
   「지금 상태」 첫 문단은 배경 저장(#329)과 갤러리 저장 실물화(#324)를 적는다.
3. `docs/doc-baseline.md`가 2636줄이다. 「현재 기준선」의 요약이 약 2500줄, 「기준선 이력」 표가
   98행이고 행 하나가 최대 4000자를 넘는다.
4. 부풀림의 원인이 절차에 있다. 이력 표의 조치 칸마다 "index 상태·기준선 줄 갱신"이 적혀 있다 —
   매 회차 감사가 index에 한 덩이씩 덧붙여 왔다.
5. lint 보고서 두 건은 발견 항목이 모두 닫혔는데 별도 파일로 남아 있다.

## 2. 기록 기준

이 설계 전체가 따르는 기준이다. 루트 `CLAUDE.md`에도 같은 표를 넣는다.

| 적는다 | 적지 않는다 |
|---|---|
| 여러 파일을 가로지르는 **현재 상태 종합** | 무엇이 삭제·교체·개명됐는가 같은 **변경 서술** |
| grep 앵커 — 현재 코드에 있는 식별자·경로 | PR 번호 나열, `~~취소선~~ → ✅` 식 이력 |
| gotcha — 코드만 봐서는 의도가 아님을 알 수 없는 결함 | 코드를 읽으면 바로 나오는 구현 세부 |
| 미완 상태의 의도 — stub인지 버그인지 | 해소된 미결, 닫힌 lint 발견 |
| 결정 이유 → ADR, 설계 → 스펙, 점검 규칙 → 점검 절차 | 날짜 머리말 단위의 누적 서술 |

근거: 수정 작업에서 에이전트는 문서를 읽고도 대상 코드를 직접 연다. 코드로 알 수 있는 사실을
문서에 적으면 절약이 아니라 중복이다. 반대로 질문형 작업에서 여러 파일에 흩어진 상태를 매번
grep으로 다시 조립하는 비용은 종합 한 줄이 없앤다.

### 3.1 `docs/status.md`

영역 목록(기능 축, `settings.gradle.kts`의 feature 모듈 기준):

1. 앱 진입·인증 — 스플래시·로그인·약관 (A-001·A-002)
2. 그룹 목록 (G-001)
3. 그룹 생성·참여 (A-004·A-005·S-102)
4. 그룹 설정 (S-101) — 닉네임·나가기·신고
5. 앱 설정 (S-001) — 로그아웃·회원 탈퇴
6. 캔버스 메인 (C-001)
7. 토핑 생성·배치 (C-101~C-106 중 누끼 제외)
8. 누끼 추출 (세그멘테이션)
9. 캔버스 편집 (C-301 배경·삭제)
10. 달력·지난 캔버스 (C-201)
11. 캔버스 이미지 저장
12. 푸시·딥링크
13. 튜토리얼 (디자인시스템 `ygtutorial`과 소비 화면)
14. 공통 기반 — 교차 관심사의 **gotcha만** 둔다(인증 토큰 재발급·디자인시스템·빌드/릴리즈 계보).
    구조 설명은 쓰지 않고 `architecture/`·ADR로 링크한다.
15. 서버 계약 — `docs/api/README.md`와 `docs/api/conventions.md`
    「Android 불일치」로 가는 **링크만** 둔다. 요약·건수를 복제하지 않는다(SoT 이중화 방지).

영역 형식:

```markdown
## 달력·지난 캔버스 (C-201)
- 상태: <현재형 한두 문장. 여러 파일을 가로지르는 종합>
- 앵커: `<식별자>`, `<식별자>`, `<저장소 상대 경로>`
- ⚠️ <gotcha 또는 미완 의도> (OQ-P-NNN)
- 설계: [<스펙 id>](superpowers/specs/archive/<파일>.md), [ADR-NNNN](adr/<파일>.md)
```

규칙:

- 상태는 현재형으로 쓰고, 바뀌면 덮어쓴다.
- `- 앵커:` 줄의 백틱 하나에는 **단일 식별자** 또는 **저장소 상대 경로** 하나만 넣는다.
  한정 이름(`A.b`), 인자·제네릭 표기(`f(x)`, `f<T>()`), OQ ID, 값(HEX 등)은 넣지 않는다.
- 앵커는 작성 시점 `develop` 코드(`docs/`·`wiki/` 밖)에 존재해야 한다.
- ⚠️ 줄마다 OQ ID를 붙인다. 해소되면 줄째 지운다.
- 링크 대상 경로 밖의 서술에 PR 번호·날짜·취소선·"→ ✅"를 쓰지 않는다.
  스펙 파일명 안의 날짜는 허용한다.
- 영역 목록은 코드 대조 중 합치거나 나눌 수 있다. 그 경우 이 스펙 대신 `status.md`가 정본이다.
- 전역 절 **「실기기 미확인」**을 맨 끝에 둔다. 코드로 판정할 수 없는 "실기기·실서버 확인 0회"
  항목을 OQ ID 목록으로 모은다(§4 분류 ③).

### 3.2 `docs/log.md`

```markdown
## [2026-09-21] audit | 143cda87b — #511 LLM 위키 이식
158파일 +27237/-0 · 유닛 1298 · 계측 46 · OQ 신설 405 · 해소 없음
```

- 유형: `audit`(doc-baseline 점검 회차) · `lint` · `restructure`.
- 머리줄: `## [YYYY-MM-DD] <유형> | <제목>`. `audit`의 제목은 `<develop 커밋> — <PR 번호와 한 구절>`.
- 본문: 최대 한 줄. `audit` 본문은 필드를 고정한다 —
  `<파일 수>파일 +<삽입>/-<삭제> · 유닛 <N> · 계측 <M> · OQ 신설 <ID 목록|없음> · 해소 <ID 목록|없음>`.
  원본 이력 행에 값이 없는 필드는 `?`로 쓴다.
- `## `로 시작하는 줄은 항목 머리줄만 허용한다. 형식 설명 같은 다른 H2를 두지 않는다
  (파일 머리 설명은 H1 아래 인용문으로 둔다).
- 오래된 것이 위, 새 것이 아래.
- 초기 이관 순서: doc-baseline 이력 표는 정렬이 섞여 있다 — 앞 약 25행은 최신이 위, 그 뒤는
  대체로 오래된 것이 위이고 일부 행이 제자리를 벗어나 있다. 내림차순 구간만 뒤집은 뒤 날짜로 안정
  정렬해 같은 날짜 안의 실제 순서를 보존한다. lint 2건(2026-07-06·2026-07-22)은 날짜 순 자리에
  끼워 넣고, 같은 날짜 audit가 있으면 그 뒤에 둔다. 끝에 이 작업의
  `restructure` 1건을 둔다.
- 검색: `grep "^## \[" docs/log.md | tail -5`.

### 3.3 `docs/doc-baseline.md`

- 머리말: 역할 인용문과 "기준선이 두 개" 인용문은 유지한다.
- 「현재 기준선」 — 절 이름을 유지한다(`open-questions` 4557·5593줄 해소 메모가 이 절을 가리킨다).
  필드는 다음과 같다.
  - repo
  - 커밋
  - 검증일(회차)
  - 테스트 수 — 유닛 N · 계측 M (다음 회차의 증감 기준)
  - 미머지 추적 항목
  - 실기기 미확인 이월 — `status.md` 「실기기 미확인」으로 링크
- 「점검 절차」 수정:
  - 로컬 경로 안내(`wiki/personal-private/project-paths.md` — 이 저장소에 없다)를 삭제하고,
    명령을 저장소 루트에서 실행하는 형태(`git -C <TJYG-Android>` → `git`)로 고친다.
  - 3단계: 드리프트 발견 → 관련 문서 수정 + **`status.md` 해당 영역 덮어쓰기**. index에는 쓰지 않는다.
  - 4단계: 「현재 기준선」 필드 교체 + **`log.md`에 `audit` 항목 추가**(§3.2 형식).
  - §4 분류 ④로 모은 절차 노하우를 판정 규칙으로 흡수한다. 예: "스펙이 부분 머지된 라운드는
    아카이브 대신 ① `status: in-progress` ② 고쳐진 자리만 표시 ③ 계획 체크박스 닫기".
- 「기준선 이력」 표를 삭제한다(→ `log.md`).

### 3.4 `docs/index.md`

- 머리말 인용문 두 개(이관 기준점, "이 파일부터 읽어라")는 유지한다.
- 「지금 상태」: 플랫폼·스택 한 문단 + "기능별 현재 상태는 `status.md`" 링크.
  기능 상태는 쓰지 않는다.
- 「무엇을 찾는가」: 셀 안의 이력 서술을 제거한다. `status.md`(기능별 현재 상태·알려진 결함)와
  `log.md`(언제 무엇을 점검했나) 행을 추가한다.
- 「문서 지도」: lint 보고서 두 줄을 지운다. `synthesis/` 설명 "(open-questions·lint)"를
  "(open-questions)"로 고친다. doc-baseline 줄의 기준선 요약을 지우고 역할 한 줄만 남긴다.
  `status.md`·`log.md` 줄을 추가한다.
- 「규율」은 유지한다.

## 4. 정보 손실 방지 — 추출 단계

**§5 코드 대조와 모든 삭제보다 먼저** 하는 독립 단계다.

1. 대상: index 전체(「지금 상태」 절과 그 뒤 라우팅 표·문서 지도), doc-baseline 「현재 기준선」 요약과
   「기준선 이력」 표 전부, lint 보고서 두 건. 추출 전에 원본 사본을 스크래치패드에 떠 두고 원문 위치는
   그 사본 기준으로 적는다(이후 태스크가 원본을 덮어쓰기 때문이다).
2. 추출: ⚠️·❌·📌 표시가 붙은 서술, "미결"·"미조치"·"실기기"·"실서버"가 나오는 서술, 그리고
   "직전 회차가 확인한 것"·"규율"·"판정 기준"·"다음 회차" 같은 절차 서술.
   원문 위치(파일:줄)를 함께 적는다.
3. 분류 — 항목마다 하나를 고른다.
   - ① 코드 관련, OQ ID 있음, 열려 있음 → 해당 영역 `status.md` ⚠️ 후보
   - ② 코드 관련, OQ ID 없음 → §5 영역 대조에서 유효성 판정. 유효하면 `open-questions` 신설
     (`oq-next`부터) 후 ⚠️, 아니면 버림
   - ③ 코드로 판정 불가(실기기·실서버·프로세스) → 기존 OQ에 붙이거나 `status.md` 「실기기 미확인」
   - ④ 절차 노하우 → doc-baseline 「점검 절차」로 승격
   - ⑤ 해소됨·중복 → 버림(사유 한 줄)
4. 산출: 스크래치 파일의 추출표(원문 위치·요지·분류·대상 영역). 저장소에 커밋하지 않는다.
5. ①②는 영역별로 나눠 §5 서브에이전트 입력으로 넘긴다.
6. 그 밖의 세부는 git 이력에 남는다. 드리프트 결과는 이미 스펙 as-built와 OQ에 반영돼 있다.

## 5. 코드 대조 방식

- 서브에이전트가 영역을 나눠 맡아 코드를 대조한다. 영역끼리 독립이라 병렬로 돈다. 에이전트 수를
  줄이려고 한 에이전트가 영역 여러 개를 맡을 수 있다.
- 대조 기준 코드는 작업 브랜치 HEAD의 워킹 트리다(doc-baseline 커밋 `143cda87b` 이후 문구 수정 머지
  하나만 더 들어와 있다). `status.md` 머리말에 기준 커밋을 적는다.
- 입력: 해당 영역에 관한 index 서술 · §4 추출표 중 해당 영역 몫 · 관련 스펙 · 열린 OQ 목록.
- 산출: §3.1 형식의 영역 초안 + 분류 ② 항목의 판정 + 버린 주장과 그 이유(보고용, 파일에 쓰지 않음).
- 모순되는 주장은 코드를 정답으로 판정한다(규율의 SoT 우선순위 "코드 > wiki > CLAUDE.md").
- 서브에이전트 브리프에 [`docs/code-conventions.md`](../../code-conventions.md)와 §2·§3.1 규칙을 링크한다.

## 7. 검증

모든 명령은 저장소 루트에서 실행한다.

```bash
# 링크 — exit 0
python3 docs/script/check_links.py docs

# 스크립트 테스트 — OK
python3 -m unittest discover -s docs/script -p 'test_*.py'

# 줄 수 — index ≤ 100, doc-baseline ≤ 80
wc -l docs/index.md docs/doc-baseline.md

# 앵커 — 출력 0줄
grep '^- 앵커:' docs/status.md | grep -o '`[^`]*`' | tr -d '`' | while read -r s; do
  case "$s" in
    */*) git ls-files --error-unmatch -- "$s" >/dev/null 2>&1 || [ -d "$s" ] || echo "MISSING path: $s" ;;
    *)   git grep -qwF -- "$s" -- ':!docs' ':!wiki' || echo "MISSING symbol: $s" ;;
  esac
done

# 금지 형식 — 링크 대상을 지운 뒤 검사, 출력 0줄
sed -E 's/\]\([^)]*\)/]/g' docs/status.md | grep -nE '#[0-9]+|~~|→ ✅|20[0-9]{2}-[0-9]{2}-[0-9]{2}'

# 로그 형식 — 출력 0줄
grep -nE '^## ' docs/log.md | grep -vE '^[0-9]+:## \[[0-9]{4}-[0-9]{2}-[0-9]{2}\] (audit|lint|restructure) \| '

# 옛 참조 — 출력 0줄
grep -rn 'lint-2026-0\|personal-private\|sync-tjyg-develop-baseline' docs --include='*.md' | grep -v '/archive/\|superpowers/specs/2026-09-26-\|superpowers/plans/2026-09-26-\|docs/log.md\|synthesis/open-questions.md\|plans/2026-08-05-orchestration\|plans/2026-08-28-login-debug\|specs/README.md'
```

손실 방지: §4 추출표의 모든 항목이 ①~⑤ 중 하나로 분류되고, ①②③④는 도착 위치(`status.md` 줄,
OQ ID, 「점검 절차」 규칙)가 확인된다.

앵커 선언 검사는 macOS git이 `\b`를 지원하지 않으므로 `([^A-Za-z0-9_]|$)`로 경계를 잡는다.
