> 사용자가 "develop 기준 문서 점검"을 요청하면, 아래 기준선부터 현재 `origin/develop`까지의 **delta(신규 머지)만** 감사하고, 끝나면 기준선을 갱신한다.

> 이 기준선과 축이 다른 또 하나의 기준선이 있다 — 이관 자체의 기준점(원본 저장소
> 커밋), [`docs/index.md`](index.md) 머리말 인용문에 있다. 이쪽은 "코드 대비 문서가
> 최신인가", 저쪽은 "이 트리를 언제 어디서 복사해 왔는가"를 잰다. 서로 다른 것을
> 재므로 하나로 합치지 않는다.

## 점검 절차 (다음 요청 시)

1. **최신화**: `git fetch origin develop`
2. **신규 머지 나열**: `git log --oneline --merges <기준선>..origin/develop`
   - 각 머지가 건드린 컴포넌트·모듈: `git show --stat <merge-hash>`
3. **문서 대조**: 변경된 심볼이 문서와 어긋나는지 검사한다.
   - 관련 spec/plan `status`·`related_code`, `architecture/*` 인벤토리, `synthesis/open-questions.md` 미머지 항목.
   - 드리프트 발견 → 해당 문서 수정 + [`status.md`](status.md) 해당 영역 **덮어쓰기**. `index.md`에는 쓰지 않는다.
   - 구현 완료분: spec → `implemented`·`specs/archive/`, plan → `done`·`plans/archive/`.
4. **기록**: 위 「현재 기준선」 필드를 전부 교체하고 [`log.md`](log.md)에 `audit` 항목 하나를 추가한다(형식은 그 파일 머리말 인용문).
5. **미머지 재확인**: `git ls-tree -r --name-only origin/develop | grep <심볼>`.

### 판정 규칙

기준선·회차
- 회차 번호는 직전 회차 번호 + 1이다. 같은 날 여러 회차가 돌 수 있어 날짜로 구분하지 않는다.
- 4단계에서 커밋만 바꾸고 검증일(회차)·테스트 수를 빠뜨리는 누락이 반복됐다. 필드를 전부 교체한다.
- 「현재 기준선」이 `log.md` 최신 `audit`와 어긋나 있으면, 두 커밋 모두에서 도달할 수 없는 머지만 새 delta로 잡는다(`git log --merges origin/develop ^<A> ^<B>`).

감사 범위·아카이브
- 감사와 아카이브의 기준은 `develop` 머지다. release 머지나 브랜치 구현만으로는 아카이브하지 않고, 미머지 브랜치의 스펙·계획 `status`도 건드리지 않는다(OQ-P-311).
- 스펙이 부분 머지된 라운드는 아카이브하지 않는다 — ① 스펙 `status`를 `in-progress`로 ② 본문에서 이번에 고쳐진 자리만 표시 ③ 계획의 해당 체크박스를 닫는다. 남은 조건부 서술은 근거로 둔다.
- 계획을 아카이브할 때 수행하지 않은 조건부 Step은 체크하지 않고 각주를 단다.
- 순서가 계약인 PR 스택은 머지된 순서부터 확인한다.
- 선작성 스펙이 있는 머지는 감사가 아니라 스펙 결정과 코드의 대조다. 스펙의 미결은 OQ로 옮긴다. 선작성 계획이 낡았으면 새로 설계하지 말고 브랜치에서 풀린 답을 가져온다.
- 문서가 "달라지지 않았다"고 단정한 자리도 감사 대상이다. 커밋 제목뿐인 변경은 코드를 직접 대조한다.
- `api/` 문서의 `verified`는 서버 계약 대조일이다. 앱 쪽 소비만 바뀐 회차에는 갱신하지 않는다.
- 색값만 바뀐 머지는 문서를 고치지 않고 기준선만 갱신한다(색값은 문서에 적지 않는다). hex 금지 규율 이전에 쓰인 아카이브 문서의 Figma hex는 보존하고 위반으로 세지 않는다.

미머지 브랜치
- 미머지 추적 항목은 parfait 문서가 걸린 브랜치만 센다. 대응 브랜치가 없는 미착수 계획 단계는 세지 않는다. 원격 브랜치 존재는 `git ls-remote`로 확인한다.
- 미머지 브랜치에 대해 미결에 단 메모는 예고다. 머지 전에는 스펙을 고치지 않고 미결에 메모만 단다. 미결이 걸린 브랜치는 코드를 직접 읽어 답을 미리 적어 두고, 머지 회차에는 그 메모를 대조표로 써서 상태만 바꾼다.
- 미결이 걸리지 않은 미머지 브랜치의 한 줄 메모는 존재 표시로만 읽고, 머지 회차에 범위를 처음부터 훑는다.

미결 판정
- 심볼이 생겼다는 것과 미결이 닫혔다는 것은 별개다. 미결 물음에 실제로 답하는지, 지금 코드가 어느 쪽인지로 판정한다.
- 미결은 문서가 정한 순서와 다르게 닫힐 수 있다. 그때는 예고와 실제가 갈린 지점, 새로 생긴 상수, 위험을 흡수한 장치를 새 미결이나 해소 메모에 옮겨 적는다.
- 기존 미결이 이미 덮는 사실이면 새 미결을 세우지 않는다. 미결을 적을 때 선행 조건이 진짜 선행인지 확인하고, 후속으로 정리할 자리에는 OQ 번호를 적는다.
- 걷어냈던 축이 되살아나는 회차에는 걷어낼 때 적은 물음 목록을 한 줄씩 대조한다.
- delta에 바이너리가 있으면 형식을 열어 구조값을 정본과 대조한다. 변경 내용이 커밋 메시지나 동반 텍스트에 남았는지 보고, 없으면 미결로 세우며 회귀 감지 수단이 있는지 따로 묻는다.

lint
- 코드 대조는 이 절차가 맡는다. lint는 상대 링크·wikilink, 상태표↔frontmatter, 규율(라인번호·변동수치·hex), 민감 데이터, 고아 문서를 본다.
- lint 결과는 별도 보고서로 남기지 않는다. 고친 것은 [`log.md`](log.md)에 `lint` 한 줄, 못 고친 것은 open-questions 항목이다.

> 드리프트는 대개 문서 검증일 이후 머지된 PR에서 생긴다. merge 날짜와 문서 `verified` 날짜를 비교하면 후보를 빨리 좁힐 수 있다.
