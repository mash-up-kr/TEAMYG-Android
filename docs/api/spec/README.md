# 팀 API 명세서 (기획 원문)

서버팀이 작성한 **API 명세 원문**을 텍스트로 옮겨 둡니다. 상위 `parfait/api/`의 도메인 계약 문서가
**서버 코드의 미러**라면, 여기는 **팀이 합의한 의도**입니다.

> **두 축을 왜 나누는가** — 명세는 *무엇을 만들기로 했는가*, 코드는 *무엇이 실제로 있는가*입니다.
> 둘이 갈릴 때 그 차이가 가장 중요한 정보이고, 실제로 갈립니다(미구현 항목, 코드에서 읽을 수 없는
> 클라이언트 측 책임, 명세에 없는 서버 동작). 한 문서에 섞으면 어느 근거로 적힌 문장인지 구분이 사라집니다.

## 무엇이 여기 들어오는가

- 코드에서 **읽을 수 없는** 계약 — 클라이언트 측 책임, 값의 생성 주체, 호출 순서, 보안 의도
- 명세에는 있으나 **서버에 아직 없는** 것 — 미구현 상태 코드·필드
- 값의 **의미**(코드에는 숫자만 있는 것) — 토큰 수명, 만료 정책

## 무엇이 들어오지 않는가

- **개인 식별 정보** — 작성자·리뷰어 실명, 코멘트, 담당자 지정. 이 repo는 public입니다.
  명세 페이지의 코멘트 스레드는 옮기지 않습니다.
- 스크린샷·이미지 원본. grep·diff가 되지 않아 자산이 되지 않습니다 — 반드시 텍스트로 옮깁니다.
- 서버 코드로 확인 가능한 사실의 **복제**. 그건 상위 도메인 문서 몫입니다.
  여기에는 명세 원문이 말하는 바를 적고, 코드와의 차이는 `## 코드 대조` 절에 씁니다.

## 파일명

`<도메인>-<기능>.md` — 예: `auth-kakao-login.md`. 상위 도메인 문서와 마찬가지로 날짜 접두사를 붙이지
않습니다(살아있는 문서, 판본은 frontmatter가 기록).

## Frontmatter

| 필드 | 내용 |
|---|---|
| `id` | 파일명(확장자 제외) |
| `title` | 명세 페이지 제목 |
| `spec_source` | 명세 출처(도구명 수준까지만 — URL·작성자 금지) |
| `spec_status` | 명세가 스스로 밝힌 상태(예: `완료`) |
| `spec_issue` | 명세가 참조하는 이슈 번호 |
| `server_commit` | 코드 대조에 쓴 서버 커밋 |
| `verified` | 코드 대조일 `YYYY-MM-DD` |
| `related_api` | 대응하는 상위 도메인 문서 |
| `tags` | `[api, parfait, spec, <도메인>]` |

## 본문 절

1. **개요** — 명세가 서술한 흐름
2. **요청 / 응답** — 명세가 제시한 필드·예시
3. **상태 코드** — 명세가 열거한 것
4. **코드 대조** — 서버 코드와 **일치 / 코드에만 / 명세에만**으로 갈라 적습니다.
   이 절이 이 문서의 존재 이유입니다.
5. **Android 구현 시 주의** — 명세에서만 얻을 수 있는 클라이언트 측 요구

## 갱신

명세가 개정되면 이 문서를 고치고 `## 코드 대조` 절을 다시 돌립니다. 서버 코드가 바뀐 경우는
스킬 `sync-teamyg-server-api`가 상위 도메인 문서를 갱신하면서 여기 `## 코드 대조` 절도 함께 봅니다.
