# 빌드 캐시 측정 하니스

**이 하니스가 답하려는 질문**: 리모트 빌드 캐시를 세우면 개발자가 실제로 얼마를 버는가?

설계 근거·용어(`T_local`·`T_remote`·시나리오 정의·집계 규칙)는 `team-yg-pesonal-agent` 레포의
`parfait/specs/2026-09-14-build-cache-measurement-harness.md` 스펙 문서에 있다. 이 README는
사용법만 다룬다.

## 선행 조건

`:app:assembleDebug`를 대상에 넣으면 아래 파일이 필요하다. 전부 `.gitignore` 대상이라
클론마다(측정 전용 worktree 포함) 각자 채워야 한다.

- 루트 `local.properties` — `sdk.dir`, `kakao.native.app.key`, debug 키스토어 관련 값
  (템플릿은 `local.default.properties`).
- 루트에 debug 키스토어 파일 3종(경로는 `local.properties`가 가리키는 값).
- `app/google-services.json`.

`--tree`로 트리를 빌리면 그 트리에 이미 있는 파일을 그대로 쓴다. `run.sh`가 새 worktree를
만드는 경우(`--tree` 생략) 저장소 루트의 `local.properties`·`app/google-services.json`을
자동으로 복사하므로, 최소한 원본 체크아웃에는 두 파일이 있어야 한다. `test` 그래프만 돌릴
때는 서명·google-services를 타지 않아 조건이 더 얕다.

## 시나리오

| ID | 사전 상태 | 무엇을 말해주는가 |
|---|---|---|
| S0 | 아무것도 지우지 않고 재실행 | 하한선. 어떤 캐시도 이 아래로 못 내려간다. |
| S1 | 빌드 출력 삭제, 캐시는 같은 커밋으로 채워진 상태 | 로컬 캐시의 최상 조건. 여기서 남는 미스는 캐시 불가 태스크다. |
| S2 | 빌드 출력 삭제 + 캐시 비움 | 총 캐시 가능 작업량. 참고값이다. |
| S3 | 커밋 B로 체크아웃, 캐시엔 A만, 출력은 A 기준 | `T_local` — 리모트 캐시가 없는 지금의 개발자. |
| S4 | 커밋 B로 체크아웃, 캐시엔 A와 B 모두, 출력은 A 기준 | `T_remote` — CI가 B를 이미 구워 둔 상태. |

`S3`·`S4`만 `--pair <A>:<B>`가 필요하다. `S0`·`S1`·`S2`는 커밋을 오가지 않으므로 `--pair` 없이
단독 실행할 수 있다.

## 경고

- **`clean`이 대상 트리의 빌드 출력을 지운다.** 모든 시나리오의 사전 상태 수립이 `clean`으로
  시작한다. 측정 전용 트리가 아니라 개발자가 실제로 쓰는 체크아웃을 `--tree`로 넘기면 그
  체크아웃의 `build/` 산출물이 사라진다.
- **`S3`·`S4`는 전용 worktree(또는 `--tree`로 받은 트리)를 커밋 사이로 오가며 돈다.** 측정이
  끝나기 전에 그 디렉토리에서 다른 작업(빌드·커밋·IDE 인덱싱)을 하지 마라. `checkout`이
  중간에 부딪히거나 엉뚱한 커밋에서 측정된 값이 섞여 나온다.
- **`--tree`로 트리를 빌려주면 그 트리의 HEAD가 측정 중 커밋 사이를 오간다.** 측정이 끝나면
  러너가 원래 HEAD로 되돌리지만(`trap`), 중간에 강제 종료하면 detached HEAD로 남을 수 있다.
  `git status`로 확인하고 필요하면 원래 브랜치로 `checkout` 하라.

## 실행 예시

**가벼운 확인용** — 하니스가 제대로 도는지만 본다. 커밋 쌍이 필요 없는 `S1`·`S2`만 돌린다.

```
./tools/build-cache-bench/run.sh \
  --scenarios S1,S2 \
  --targets :core:util:jvm:compileKotlin \
  --iterations 1
```

**전체 측정용** — 커밋 쌍을 정하고(아래 [커밋 쌍 선정 절차](#커밋-쌍-선정-절차-필수) 참고)
5개 시나리오를 3회 반복으로 돌린다.

```
PAIR_A=$(git rev-parse <A>)
PAIR_B=$(git rev-parse <B>)
./tools/build-cache-bench/run.sh \
  --scenarios S0,S1,S2,S3,S4 \
  --targets :app:assembleDebug,test \
  --pair "$PAIR_A:$PAIR_B" \
  --iterations 3
```

`--dry-run`을 붙이면 빌드 없이 실행 계획(시나리오 × 대상 × 회차 목록)만 출력한다.

## 커밋 쌍 선정 절차 (필수)

`run.sh`의 `validate_pair`는 `--pair`로 받은 두 커밋이 **존재하는지만** 확인한다. "대상
그래프의 입력이 실제로 바뀌는가"는 보지 않는다. 두 커밋 사이에 측정 대상 모듈의 소스가
바뀌지 않으면 `S3`·`S4`가 **둘 다 `UP_TO_DATE`로 끝나 핵심 값(`S3 − S4`)이 0에 수렴하고도
에러 없이 통과한다.** 러너는 이 상황을 감지하지 못한다.

쌍을 고를 때는 먼저 아래로 입력 변화를 확인하라.

```
git diff --stat <A> <B> -- <대상 모듈 경로>
```

출력이 비어 있으면 그 쌍은 쓰지 않는다. 실제로 이 저장소에서 `HEAD~1:HEAD`가 이 조건에
걸려 무신호였던 사례가 있다.

## 무신호를 알아보는 법

`summary.md`의 적중률 표에서 `S3`가 전부 `UP_TO_DATE`이거나, 핵심 값 표의 차이가 0에 가깝게
나오면 **캐시 효과가 없다고 결론 내리지 마라.** 그보다 먼저 **커밋 쌍이 잘못 골라졌을
가능성**을 의심하라 — 위 [커밋 쌍 선정 절차](#커밋-쌍-선정-절차-필수)로 대상 모듈의 입력이
실제로 바뀌는 쌍인지 다시 확인한다.

## 결과 읽는 법

`summary.md`의 핵심 값은 **`S3 − S4`(`T_local − T_remote`)이지 `S2 − S1`이 아니다.**

- `S2 − S1`은 "로컬 캐시를 통째로 비웠다가 다시 채우는 비용"이다. 개발자가 매일 겪는 일이
  아니다.
- `S3 − S4`는 "새 커밋을 당겨받았을 때, 그 커밋의 항목이 로컬 캐시에 없는 경우(`S3`)와
  CI 캐시에서 받아 올 수 있는 경우(`S4`)의 차이"다. 이것이 리모트 빌드 캐시가 실제로 파는
  물건이다.

`S1`·`S2`는 그 차이를 해석하기 위한 참고값이다 — `S1`은 로컬 캐시가 낼 수 있는 최선,
`S2`는 캐시가 전혀 없을 때의 총 작업량이라, `S3 − S4`가 그 사이 어디에 놓이는지 가늠하게
해 준다.

## 측정 조건

- 모든 Gradle 호출은 `--offline`으로 고정한다. 의존성 캐시가 있어도 플러그인 마커 재확인이나
  툴체인 해석에서 네트워크가 낄 수 있어서다.
- 회차(iteration)마다 Gradle 데몬을 `--stop`으로 재기동한 뒤 `help`를 1회 실행해 워밍업한다.
  사전 상태를 만드는 빌드 횟수가 시나리오마다 달라 데몬 온도가 갈리기 때문에, 측정 직전에는
  모든 회차가 같은 조건에서 출발하도록 맞춘다.
- **IDE(Android Studio)를 닫고 돌려라.** 유휴 Gradle 데몬이 있으면 러너가 경고하지만 막지는
  않는다. 다른 데몬이 살아 있으면 수치가 흔들린다.
- 반복 횟수는 `--iterations`로 받고 중앙값을 쓴다. **반복이 짝수면 중앙값은 아래쪽 값이다**
  (평균이 아니다) — BSD `awk`에 `asort`가 없어 정렬은 `sort`에 맡기고 가운데(또는 가운데
  아래) 인덱스를 그대로 집는다.

## 한계

- **OS 이식성은 확인되지 않는다.** CI는 `ubuntu-latest`이고 개발자는 macOS다. CI가 만든 캐시
  항목이 개발자 머신에서 적중하는지는 이 하니스로 알 수 없다(별도 게이트 `check-relocatability.sh`가
  절대경로 이식성만 확인한다).
- **전송 시간이 반영되지 않는다.** `S4`(`T_remote`)는 캐시 다운로드·압축 해제 시간을 0으로
  가정한다. 그래서 `S3 − S4`는 **낙관적 상한**이지 실제 이득이 아니다.
- **Kotlin 데몬은 `./gradlew --stop`으로 죽지 않는다.** 회차마다 재기동되는 것은 Gradle
  데몬뿐이라 Kotlin 컴파일 쪽 웜업 곡선은 통제되지 않는다. `builds.csv`의 `daemon_pid`로
  Gradle 데몬이 실제로 교체됐는지만 사후 확인할 수 있다.
- **`clean`이 지우지 않는 상태가 남는다.** `<tree>/.gradle`의 파일 해시·실행 이력,
  `~/.gradle/caches/<버전>/transforms-*`는 그대로 남는다. 그래서 `S2`는 "캐시 축출 직후"이지
  "새 머신"이 아니다.
- **머신마다 수치가 다르다.** 서로 다른 머신에서 잰 값을 직접 비교하지 않는다.

## 산출물

`--out`(기본 `runs/<타임스탬프>/`) 아래에 남는 파일:

- `builds.csv` — 빌드 1행. 컬럼: `scenario,target,pair,iteration,wall_ms,daemon_pid`.
- `cache-size.csv` — 시나리오별 캐시 항목 수·용량. 컬럼: `scenario,target,iteration,entries,kb`.
- `tasks/<시나리오>-<대상>-<회차>.csv` — 태스크 1행. 컬럼: `task_path,outcome,duration_ms,execution_reasons`.
- `logs/<태그>.log` — 해당 빌드의 Gradle 전체 로그. `<태그>.prepare.log`·`<태그>.warmup.log`는
  사전 상태 수립·워밍업 로그로, 측정 대상 로그와 구분된다.
- `summary.md` — 이 README의 [결과 읽는 법](#결과-읽는-법)대로 정리된 사람이 읽는 요약.

`runs/`는 `.gitignore` 대상이다. 측정치는 머신마다 다르므로 커밋하지 않는다.
