# 앱 닉네임 생성 정책 v0.1 (S-002)

## 요약

**초기 앱 닉네임을 어떻게 자동으로 만드는지**를 처음 정한다. 뒤이어 수정 시
유효성 규칙과 적용 범위를 적는데, **유효성 규칙 쪽은
[[src-S-002-앱닉네임-정책-v0.1]]과 글자 하나까지 같다.**

**날짜도 버전도 작성자도 개정이력도 없다.** 머리말 자체가 없고 제목
`# S-002 앱닉네임 정책`으로 바로 시작한다. [[src-Toast-공통-정책]]에 이어 **두
번째**다.

**[[src-S-002-앱닉네임-정책-v0.2]](07-25)가 가리키는 노션 문서로 읽힌다.** 그
문서는 자동 생성 절에서 단어 목록을 싣지 않고 **"형용사/동사 100개, 파르페 재료
30개는 노션 참고"**라 적는데, **그 100개와 30개를 실제로 가진 소스는 이것뿐**이다.
머리말이 없고 `[K2]`와 구현 쪽 주석까지 담은 작업 메모 꼴인 것도 맞는다. **다만
링크가 전사되지 않아 확인할 수 없다**([[open-questions]]).

## 07-22보다 뒤다

**문서 안에 선후를 세울 근거가 하나 있다.** §1.1이 `G-001` 토핑 회전 로직의
**`Math.random()` 금지 규정**을 들어 자신과 구별한다. 그 규정은
[[src-G-001-무한파르페-정책설계-v0.3]] 계열이 정한 것이므로 **이 문서는 그보다
뒤에 쓰였다.**

**같은 화면의 앞 문서(07-02)와 날짜 차이가 최소 3주다.**

## 닉네임을 3000가지로 만든다

| 항목 | 내용 |
|---|---|
| 시점 | **계정 생성 시 1회** |
| 방식 | `형용사/동사` 100개 × `파르페 재료` 30개에서 **각 1개 랜덤 조합** |
| 형식 | `{형용사/동사}{재료}` — **공백 없이 붙여쓴다** |
| 저장 | **계정 생성 즉시 DB 저장.** 이후 재계산하지 않는다 |
| 조합 수 | **3000** |

예시는 `녹는딸기`, `몽글한푸딩`, `스며드는블루베리`, `말랑한커스터드`,
`톡톡튀는스프링클`, `단카라멜`이다.

**풀에 중복 항목은 없다** — 형용사 100개, 재료 30개 모두 서로 다르다.

### 반복 표현이 풀의 절반을 이룬다

형용사 풀은 같은 말의 변주를 나란히 넣는다 — `몽글한`/`몽글몽글한`,
`퐁신한`/`퐁신퐁신한`, `폭닥한`/`폭닥폭닥한`, `말랑한`/`말랑말랑한`,
`보송한`/`보송보송한`, `사각거리는`/`사각사각한`. `녹-` 계열만 여섯이다
(`녹는`·`녹아드는`·`녹아내리는`·`녹아버린`·`녹여버린`·`녹인`).

**빈 토핑 템플릿 6종이 세 형태의 변주 둘씩이었던 것과 같은 짜임이다**
([[src-G-001-그룹-토핑-템플릿-정책-v0.2]]).

## 디저트 어휘가 한 풀을 공유한다

재료 30개는 딸기 / 바나나 / 키위 / 블루베리 / 복숭아 / 체리 / 파인애플 /
오렌지 / 메론 / 무화과 / 바닐라 / 초콜렛 / 딸기슈 / 가나슈 / 커스터드 / 우유 /
그래놀라 / 오레오 / 카스테라 / 케이크 / 젤리 / 푸딩 / 연유 / 카라멜 / 아몬드 /
슈가파우더 / 딸기시럽 / 스프링클 / 쿠키 / 비스킷이다.

**이 풀이 제품의 다른 어휘와 겹친다.**

| 어디 | 겹치는 것 |
|---|---|
| 프로필 칩 컬러 이름([[account]]) | **체리 · 메론 · 푸딩** (그리고 바닐라·초콜렛도 풀에 있다) |
| 폐기된 빈 토핑 템플릿 6종([[src-G-001-그룹-토핑-템플릿-정책-v0.1]]) | **딸기 · 키위 · 오레오** |

[[parfait]]의 디저트 은유가 화면 구조와 팔레트를 지나 **사람의 이름까지**
내려왔다. 빈 토핑 템플릿에서 물러난 어휘가 **여기서는 그대로 쓰인다.**

## 10자 이내를 하나가 넘는다

[[src-기능정의서-v6]]의 `A-002`는 신규 사용자 닉네임을 **"랜덤부여(10자
이내)"**라 적는다.

**3000개 조합 중 정확히 하나가 11자다** — `바스락거리는슈가파우더`
(형용사 최장 `바스락거리는` 6자 + 재료 최장 `슈가파우더` 5자). 나머지 2999개는
10자 이하이고 최단은 `단딸기` 3자다.

> ⚠️ [2026-09-17] [[src-기능정의서-v6]] 와 상충 — 기능정의서가 랜덤 부여를 10자
> 이내로 적는데 이 풀은 11자 조합을 하나 만든다. 3000분의 1이라 테스트로 잡히지
> 않는다 → [[open-questions]]

**수정 상한 15자와는 어긋나지 않는다.** 문제는 부여 쪽 상한 하나다.

## 생성 주체가 정해지지 않았고 마커가 붙었다

> **[K2]** 서버에서 생성 후 응답으로 내려주는지, 클라이언트가 생성해서 서버로
> 올리는지 확정 필요.

원본이 **권장까지 적었다** — 계정당 유일성이 필요 없다면 클라이언트 생성도
가능하나, **어뷰징·치우침 방지 관점에서는 서버 생성 권장**이다.

**근거가 달린 미정이다.** 고르지 않았지만 무엇을 보고 골라야 하는지는 적혔다.

**`[K2]`는 이 위키가 처음 보는 표기다.** 화면 ID와도, 툴팁·컴포넌트 문서의
일련번호와도 다른 축이다. `K1`이나 `K3`이 무엇인지는 이 문서에 없다
([[screen-id-scheme]]).

**서버 담당은 여전히 배정되지 않았다** — 서버가 들고 있어야 할 것이 또 하나
늘었다([[open-questions]]).

## 다른 화면의 규정을 끌어와 자신을 구별한다

§1.1이 괄호 안에서 이렇게 적는다 — 재렌더링 시점에 다시 뽑지 않는 것은
**`G-001` 토핑 회전 로직의 `Math.random()` 금지 규정과는 별개 사안**이고,
토핑 회전은 매 렌더마다 같은 결과가 나와야 하는 반면 닉네임은 1회성 부여 후
고정값이라 **난수 소스 제약이 다르게 적용**된다.

**정책서가 다른 화면의 규칙을 인용해 자기 규칙을 구별한 첫 사례다.** 이 위키가
문서들을 겹쳐 놓고서야 찾아내던 종류의 구별을 원본이 먼저 했다 —
[[src-S-101-프로필-이미지-및-그룹칩-내-타임스탬프-컬러-규칙-v0.1]]이 컬러 표
차이를 스스로 해명한 것과 같은 결이다([[spec-version-history]]).

**다만 인용이 정확하지는 않다.** 정책설계 `v0.3`이 정한 것은
**"재추첨 시점은 목록 조회 응답 1회, 리렌더·셀 재사용에서 다시 뽑는 것은 금지"**
이고 근거는 "회전각 튐 방지"였다. `Math.random()`이라는 함수 이름은 어느 소스에도
없다 — **구현 어휘로 옮겨 적은 것**이다.

## 유효성 규칙은 앞 문서와 같다

§2·§3이 [[src-S-002-앱닉네임-정책-v0.1]]의 §1·§2와 **규칙 줄 열넷이 글자 하나까지
같다.** 통과·불통과 예시(`홍 길동`, `홍  길동`, `열다섯글자` × 3)도 같다.

| 항목 | 규칙 |
|---|---|
| 허용 문자 | 한글, 영문, 숫자, **공백**. 특수문자·이모지 불가 |
| 글자 수 | **최소 1자 ~ 최대 15자.** 글자 사이 공백도 1글자로 센다 |
| 공백 위치 | 맨 앞·맨 뒤 불가. 글자 사이는 **1칸만**, 연속 공백 불가 |

**같은 규칙을 든 문서가 다섯이 됐다**(현행 넷) — 이 문서,
[[src-S-002-앱닉네임-정책-v0.2]]와 그것이 대체한
[[src-S-002-앱닉네임-정책-v0.1]], [[src-S-102-닉네임-정책-v0.1]], 그리고 상한만
10자로 바꾼 [[src-A-005-그룹명-정책-v0.1]]이다. **`v0.2`가 그 중복이 의도임을
처음 밝혔다** — 두 화면이 나중에 갈라질 수 있어 계열을 유지한다
([[open-questions]]).

## 적용 범위가 정밀해졌다

| | 앞 문서(07-02) §3 | 이 문서 §4 |
|---|---|---|
| 그룹 내 닉네임 | "그룹 내 닉네임" | **2~3장 유효성 규칙 적용** |
| 앱 닉네임 | "초기 랜덤 닉네임 수정 시점부터 적용" | **계정 생성 시 1장(자동 생성)이 우선, 수정할 때부터 2~3장** |

**그룹 내 닉네임의 글자 수가 확정됐다.** 앞 문서도 적용 범위에 그룹 내 닉네임을
들었으나 이 문서가 **장 번호로 어느 규칙이 걸리는지 못박았다** — 1~15자,
같은 허용 문자, 같은 공백 규칙이다([[group]]).

**그리고 자동 생성이 앱 닉네임에만 걸린다는 것도 여기서 처음 분명해진다.**
그룹 내 닉네임에는 1장이 적용되지 않는다 — 가입 시 무엇이 기본값으로 들어가는지는
여전히 없다.

## 미결

- 생성 주체가 서버인지 클라이언트인지(`[K2]`). 권장은 서버다.
- 3000개 중 한 조합이 기능정의서의 "10자 이내"를 넘는다.
- 닉네임 **중복 허용 여부**와 **금칙어**는 이 문서도 다루지 않는다. `A-005`
  그룹명은 "중복 허용"이 명시돼 있고 `S-102`는 **"그룹 내 중복 정책 적용"**이라고만
  적힌다.
- 같은 유효성 규칙을 든 문서가 다섯이다. 중복이 의도라는 것은 `v0.2`가 밝혔다.
- 이 문서가 [[src-S-002-앱닉네임-정책-v0.2]]가 가리키는 노션 문서인지 링크가
  없어 확인할 수 없다.
- 그룹 가입 시 그룹 내 닉네임의 기본값이 무엇인지.
- 날짜·버전·작성자·출처가 전부 없다.
- `[K1]`·`[K3]`이 있는지, 이 마커 축이 무엇인지.

전부 [[open-questions]]에 있다.
