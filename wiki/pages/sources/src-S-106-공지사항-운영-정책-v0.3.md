# S-106 공지사항 운영 정책 v0.3

## 요약

`S-106`(앱 사이드메뉴 > 공지사항)의 운영 정책이다. 날짜 **2026-11-11**, `v0.3 (초안)`,
최종 편집 11-11(`DSN-B`). **새 계열의 첫 수집본이고, 이번에 들어온 정책 문서 중
가장 늦다.**

`v0.1`(10-31)·`v0.2`(11-03)는 수집되지 않았다. 대신 이 문서 §10이 판본별 변경을
표로 남겼다.

| 버전 | 날짜 | 요지 |
|---|---|---|
| `v0.1` | 10-31 | 최초 초안 — 공지 대상(Minor/Major), 구성, 플랫폼별 분리, 게시·알림·수정 규칙, 첫 공지 |
| `v0.2` | 11-03 | 최종 디자인 반영 — 제목 4종·안내 본문 문구, **NEW 칩 규칙**, 새 글 판단을 **공지 단위 읽음**으로, 첫 실행 초기화(`E05`) 폐기 |
| `v0.3` | 11-11 | 개발 확인 — NEW 칩 소멸 조건 확정, **웹뷰가 아닌 네이티브 화면**, 목록 NEW 칩을 제목 뒤로 |

## 왜 만들었나

- 앱 안에 공지 수단이 없어 **새 버전 안내와 약관·개인정보처리방침 개정 안내를 할 곳이
  없다.**
- **이용약관 제3조와 개인정보처리방침 제12조가 "서비스 내 공지사항(사이드 메뉴 >
  공지사항)"을 개정 고지 채널로 이미 명시**하고 있다. 공지사항은 법정 고지 수단이다.
- iOS와 Android는 패치노트가 조금씩 달라 업데이트마다 따로 나간다.

**약관이 화면보다 먼저 있었다.** 약관이 가리키는 메뉴가 앱에 없던 상태를 메우는
문서이기도 하다.

## 핵심 원칙

| # | 원칙 | 근거 |
|---|---|---|
| `P-1` | **서버가 관리하고 앱은 받은 값을 그대로 표시** | 앱 업데이트 없이 올리고 고친다 |
| `P-2` | 업데이트 공지는 **정해진 제목·날짜·패치노트 원문만** | 인사말·"스토어에서 업데이트해 주세요" 같은 문구 없음 |
| `P-3` | **Minor·Major일 때만** 업데이트 공지 | Patch까지 올리면 중요한 변화가 묻힌다 |
| `P-4` | **공지 1건 = 1플랫폼** | 배포 시점·패치노트가 달라 게시·수정이 독립된다. 공통 내용을 두 번 등록해야 하는 것이 단점 |
| `P-5` | **새 공지는 푸시 없이 NEW 칩으로만** | 푸시 종류를 새로 만들면 푸시알림 정책·이용약관 제5조의2·`S-105`가 함께 바뀐다 |

**푸시를 보내지 않기로 한 이유가 비용이다** — 사용자 피로가 아니라, 새 푸시가
[[src-푸시알림-정책-v0.4]]·약관·[[src-푸시알림-인앱-알림-제어-정책-v0.3]] 세 곳을
같이 고치게 만든다는 것이다. 범위를 좁힌 결정에 근거가 붙은 사례다
([[mvp-scope-limits]]).

## 무엇을 공지하나

공지는 두 유형이다.

| | 업데이트 공지 | 안내 공지 |
|---|---|---|
| 버전 | 필수 (예: 1.3.0) | 없음 |
| 제목 | `파르페 v{버전} 업데이트 안내` | 개정 대상별 3종 |
| 날짜 | 게시일 `YYYY.MM.DD` | 공고일 `YYYY.MM.DD` |
| 본문 | 패치노트 원문 (줄바꿈·글머리표 유지) | 시행일 안내 문장 |

- 업데이트 공지는 **Major**(대규모 개편)·**Minor**(신규 기능 추가)만. **Patch**(버그
  수정·경미한 개선)는 올리지 않는다.
- 본문은 **해당 버전 패치노트만.** 공지사항이 처음 열리는 버전부터 쓰고 **소급하지
  않는다.**
- 안내 공지 제목: `이용약관 및 개인정보처리방침 개정 안내` / `이용약관 개정 안내` /
  `개인정보처리방침 개정 안내`. 본문은 `2026년 11월 24일자로 … 개정될 예정입니다.`
- 본문 날짜는 **시행일**, 제목 아래 날짜는 **게시일(공고일)**이고 **시행일 7일
  전**이다(예: 2026.11.17).

### 첫 공지

**공지사항 오픈 버전 자체가 첫 공지다.** "푸시알림 인앱 제어 기능 추가와 묶여 나가는
Minor 업데이트"로 신규 기능이 있으니 공지 대상이다. iOS·Android 각 1건.

예시 버전이 `1.3.0`이고 `S106-E03`이 **"v1.3.0 미만 앱 유저"**를 화면이 없는 쪽으로
적는다. 공지사항과 `S-105`가 **1.3.0에 함께 나간다**는 뜻으로 읽힌다.

## 게시

- **업데이트 공지**: 해당 플랫폼 스토어에 **공개된 뒤** 게시한다. 먼저 보이면
  "업데이트가 없다"는 혼선이 생긴다. 플랫폼별 배포 시점이 다르면 따로 게시한다.
- **노출 대상**: 자기 기기 OS의 업데이트 공지와 공통(안내) 공지만 본다.
- **구버전 사용자**: 자기 앱보다 높은 버전 공지도 보인다 — 업데이트 유도 효과.
- **안내 공지**: 시행일 **7일 전**, 사용자에게 불리한 변경은 **30일 전**까지(이용약관
  제3조, 개인정보처리방침 제12조).

| 항목 | 규칙 |
|---|---|
| 수정 | 오탈자·표현은 서버에서 바로. **수정 표시 없음, 게시일 불변** |
| 삭제 | 원칙적으로 안 한다. 잘못 올리면 수정으로 정정. **안내 공지(법정 고지)는 삭제 금지** |
| 보관 | 노출 기간 제한 없이 전체를 게시일 최신순 |

운영 절차는 5단계다 — 버전 확정(Patch면 끝) → 플랫폼별 패치노트 → 스토어 공개 확인
→ 서버 등록 → 앱 노출 확인. **누가 서버에 등록하는지, 어드민이 있는지는 적혀 있지
않다.** 10-27 회의는 "어드민 구축할 것인지, 구글 사이트에서 수동 등록할 것인지"를
정하지 못했다([[src-회의록-2026-10-27-회의]]).

## 화면

- **앱 네이티브 화면이다. 웹뷰가 아니다**(`v0.3` 확정, 사유 "개발 확인"). §10은
  "BL_04에는 웹뷰로 기재"였다고 적는다.
- **목록**: 게시일 최신순. 행마다 제목, 아래 날짜, 오른쪽 화살표. NEW 대상이면 **제목
  뒤**에 `Chip-New`.
- **상세**: 카드 안에 제목·날짜·구분선·본문. NEW 칩 없음.
- **오류**: 상단 바 아래 토스트만(`S106-E07`).

**11-10 회의록 작업 표에는 `공지사항 (웹뷰)`로 적혀 있다**
([[src-회의록-2026-11-10-회의]]). 11-03 회의가 이미 "~~웹뷰~~ 네이티브"로 고쳤고
([[src-회의록-2026-11-03-회의]]) 이 문서(11-11)도 네이티브라, 회의록 표가 갱신되지
않은 것으로 읽힌다.

## NEW 칩

- 푸시는 보내지 않는다. 목록 행과 `S-001`의 `공지사항` 라벨 오른쪽에 **같은
  `Chip-New`**를 단다. 별도 뱃지를 만들지 않는다.
- **노출**: 사용자가 열어보지 않은 공지.
- **소멸**: 상세를 열면 그 공지의 칩이 사라진다. 열지 않아도 **게시 후 14일**이 지나면
  사라진다(`v0.3` 확정. 11-03 회의에서 "일주일"이 14일로 바뀌었다).
- **사이드 메뉴 칩**: 목록에 NEW가 하나라도 있으면 표시, 다 사라지면 숨김.
- **읽음 기록은 기기에만 저장한다. 서버에는 저장하지 않는다.**
- 그래서 앱 업데이트 직후·재설치·신규 설치면 14일 안 공지가 **전부 NEW**로 보인다.

**`v0.2`가 뒤집은 것**: `v0.1`은 기기에 "마지막 확인 시점"을 두고 `S-106`에 들어가면
뱃지를 해제했고, 첫 실행이면 그 시점을 현재로 초기화했다(`E05`). `v0.2`가 이 초기화를
폐기한 이유 — **업데이트한 사용자가 첫 공지의 NEW를 못 보게 되고, "재설치하면 다시
뜬다"와 모순된다.**

## 예외 케이스

| # | 케이스 | 처리 |
|---|---|---|
| `S106-E01` | 한쪽만 먼저 배포 (예: iOS 심사 지연) | 공개된 쪽만 먼저 게시 |
| `S106-E02` | 플랫폼 버전 번호가 다름 (예: 한쪽만 1.3.1) | 해당 스토어 버전을 그대로 표기 |
| `S106-E03` | v1.3.0 미만 | 화면이 없어 앱에서 볼 수 없음 |
| `S106-E04` | 자기 앱보다 높은 버전 공지 | 그대로 노출 |
| `S106-E05` | 업데이트 직후·재설치·신규 설치 | 읽음 기록 없으면 전부 안 읽음, 14일 이내에 NEW |
| `S106-E06` | 같은 날 여러 건 | 나중에 등록한 것이 위 |
| `S106-E07` | 목록 조회 실패 | 토스트 `공지를 불러오지 못했어요, 나중에 다시 시도해 주세요`. 재진입 시 재조회 |
| `S106-E08` | 공지 0건 | 빈 상태 — "이럴 일 없음". 기능 배포와 함께 첫 공지 게시 |

`S106-E02` 처리 칸에 팀원에게 하는 말("최대한 버전 번호 같게 유지하자")이 섞여 있다.
초안 표기와 맞다. 빈 상태 화면 디자인은 정의되지 않았다.

**`S-106`도 앱 레벨 메뉴 아래인데 번호가 `S-1xx`(그룹 레벨) 대역이다**
([[screen-id-scheme]]). 11-03 회의는 알림 설정·공지사항·아동 안전 정책(Android만)이
더해져 **앱 사이드 메뉴가 너무 무거워졌다**며 웹뷰 문서들(개인정보처리방침·이용약관·
아동안전정책·오픈소스 라이선스)을 묶어 아래로 내리는 안을 냈다
([[src-회의록-2026-11-03-회의]]). 이 문서는 "메뉴 내 위치·순서는 사이드 메뉴 정리
결과를 따른다"고만 적는다.
