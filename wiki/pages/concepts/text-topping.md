# 텍스트 토핑

## 정의

[[canvas]] 위에 사진이 아니라 **글자를 올리는 객체**다. 캔버스에 놓이는 것이 사진
토핑 하나에서 **사진과 텍스트 둘**이 됐다. 원본 문서들은 이것을 "텍스트"라고만
부르고 토핑이라 부르지 않는다 — 이 페이지 이름은 사진 토핑과 같은 자리에 놓인다는
뜻으로 붙였다.

**누끼를 거치지 않는 두 번째 배치 경로다**([[topping-placement-pipeline]]). 진입은
`C-001` 하단 `[추가 +]`의 2뎁스 3단 메뉴 `[카메라로 촬영 / 갤러리에서 선택 / 텍스트
입력]` 중 셋째이고, **`C-106` 텍스트 입력 → `C-106-Arrange` 텍스트 배치 →
`[캔버스에 쌓기]`**로 끝난다([[src-BL_1-텍스트-업로드-기능-추가-정책-v0.1]]).

**`C-106`은 v7에서 사진의 "캔버스에 배치"였다.** UX_1 이후 사진 배치는
`C-105-Arrange`로 가고 `C-106`은 텍스트 입력이 됐다 — ID 재사용이 또 일어났다
([[screen-id-scheme]], [[src-figma-주석-캔버스-C-SY]]).

## 원칙은 "사진과 동일하게" (10-04 정의)

10-04 회의가 공동 캔버스와 배치·조작 항목을 **"여기까지 모두 사진과 동일하게"**로
묶어 닫았다.

- 수정·삭제는 **작성자 본인만.** 남의 텍스트를 탭하면 작성자 토스트
  `XX님이 N분 전에 쌓았어요`만 뜨고 진입하지 않는다.
- 레이어는 **마지막에 쌓은 것이 맨 위.** 남의 사진·텍스트 위에도 쌓을 수 있다.
- **개수 제한 없음** — 1인당·캔버스당 모두.
- 이동 한 손가락, 크기·회전 두 손가락 핀치(배치 시에만, 작성 중엔 크기 조절 없음).
- **캔버스 밖으로 넘친 부분은 잘린다** — 사진과 같다.

## 업로드 후 수정 — 회의는 불가, 정책서는 갈린다

**결정은 수정 불가다**([[src-회의록-2026-10-06-회의]]). 근거가 넷 붙었다.

1. 사진도 수정이 안 되는데 글자만 되면 일관성이 깨진다
2. 지우고 다시 올리면 된다
3. 수정 버튼으로 depth가 늘어난다
4. 「수정됨」 표시 자리가 없고 예쁘지 않다

10-04 회의에서 이미 "업로드 후 수정 가능케 하려면 텍스트 객체 유지"라는 줄이
취소선으로 지워지고 "수정 안되는 걸루"가 적혔다. 10-10 디자인 회의는 **"수정 버튼
없음"**을 와이어프레임 반영 항목으로 체크했다([[src-회의록-2026-10-10-디자인-회의]]).

> ⚠️ [2026-11-13] [[src-BL_1-텍스트-업로드-기능-추가-정책-v0.1]] 와 상충 — 회의(10-06)와
> 그 문서의 흐름도 `U-6`은 "이후 수정 불가"인데, 같은 문서 본문 §1·§8과 수정 흐름
> `E-1`~`E-5`, 화면 `C-106-Arrange(수정 중일 시)`는 **내용·스타일까지 수정 가능**이다.
> 문서 날짜(10-09)가 회의 뒤다 → [[open-questions]]

**정책서 한 문서가 스스로 갈린다.** 수정 가능 쪽은 본문 여러 절과 Figma 프레임
([[src-figma-주석-캔버스-C-SY]])에 걸쳐 있고, 불가 쪽은 흐름도 한 줄이다.
[[src-푸시알림-정책-v0.4]]도 비트리거 목록에 "텍스트 수정(내용·스타일)"을 적어
수정이 있다는 전제로 읽힌다. **어느 쪽이 배포됐는지는 이 위키 소스로 판정되지
않는다.** 사진 쪽은 UX_1 이후 위치·크기·회전·테두리 수정이 생겼으므로
([[topping-placement-pipeline]]) 근거 1번 "사진도 수정이 안 된다"도 지금은 맞지
않는다.

## 저장 — 이미지로 굽지 않는다

**텍스트 개체로 저장한다**(이미지 합성 안 함, 10-06). 근거는 이미지 저장 비용과
"이미지는 키우면 깨진다", 그리고 "사진 토핑도 값만 내려받아 뷰로 그리므로 같게
처리 가능".

**그 결정이 데이터 계약을 바꿨다.** 그룹 리스트와 캔버스 응답에 텍스트가 섞이면서
**v2 응답**이 생기고 구버전 앱 하위 호환이 문제가 됐다. zIndex도 이슈로 적혔다
([[src-회의록-2026-10-27-회의]]). 그룹 목록의 토핑 프레임([[infinite-parfait]])에
텍스트가 어떻게 그려지는지는 정해지지 않았다.

**푸시 미리보기도 이 결정에서 나왔다** — 텍스트가 이미지가 아니라서 내용을 보여줄
수 있다. 아래 "푸시"를 본다.

여백·테두리를 조절하는 기능.

### 폰트 — 시스템 폰트를 쓰지 않는다

10-04 회의는 처음에 "시스템 폰트 하나"로 적었다가 같은 자리에서 **"시스템폰트 ㄴㄴ,
수트 다국어지원"**으로 뒤집었다. 10-06이 **1종 고정**을 결정했고 근거는 **"Android와
iOS 시스템 폰트가 달라 같은 글자가 다르게 보인다"**다 — 같은 캔버스를 두 플랫폼이
함께 보는 제품이라 자형이 갈리면 안 된다는 뜻이다.

SUIT는 **SIL Open Font License 1.1**이다([[src-회의록-2026-10-10-디자인-회의]]).
**캔버스 정책 `v0.3`의 디자인 토큰 서체도 SUIT다** — UI 서체를 텍스트 객체에도
그대로 쓴 것이다([[canvas]]).

**일본어·중국어는 정책서가 번들로 정했다.** SUIT에 일본어·한자 글리프가 없어
10-06은 "일단 찾아보고 안 되면 제외"를 달았고, 10-10은 일본어 지원 여부·중국어
범위·번들 vs 폴백·폴백 순서 네 칸을 모두 비웠다. `BL_1`이 **Line Seed JP / TW를
앱에 포함**한다고 적어 번들 쪽으로 갔다. **TW라 번체로 읽히나 간체 지원 여부는
없다.**

## 글자 수 — 100자에서 500자로

**현행 상한은 500자다.** 11-03 회의가 배포 후 피드백("100자가 너무 적다")을 받아
"일주일 안에 가능"으로 정했고([[src-회의록-2026-11-03-회의]]), 11-10이 완료로
올렸다([[src-회의록-2026-11-10-회의]]). 늘릴 수 있었던 근거는 **이미 구현된 자동
축소**다 — 줄이 늘면 글자가 작아지므로 상한을 높여도 화면이 넘치지 않는다.

`BL_1`은 여전히 **100자**로 적혀 있다. 문서가 결정을 따라가지 않은 것이다.

세는 법은 그대로다 — 띄어쓰기·줄바꿈·이모지 각 1자, **화면에 보이는 글자 단위**
(조합 이모지도 1자). 도달하면 추가 입력을 무시하고 카운터가 빨개진다. 붙여넣기로
넘치면 앞부분만 남긴다. **줄 수나 높이로는 막지 않는다.**

**11-03 피드백 중 둘은 범위 밖으로 갔다.**

- 텍스트 색상이 너무 적다 → **"언젠가하자"**(구버전 대응·색상 범위·UX 개선이 먼저)
- 줄바꿈이 마음대로 안 된다 → **"스루".** 원본이 추측한 원인 — 글자 크기 24px 고정 +
  영역 초과 시 자동 줄바꿈, 핀치로 줄여도 포커스하면 24px로 돌아온다

## 입력과 키보드

- **시스템 키보드.** 엔터는 줄바꿈이지 완료가 아니다.
- 헤더 `배치` + `✓`. **키보드가 올라와 있는 동안 `X`는 숨긴다.**
- 키보드 위 플로팅 툴바 `[색] [타입] [정렬] · 글자 수`. **타입·정렬을 눌러도 색
  팝오버는 닫히지 않는다** — 색을 고르며 타입별 모습을 비교하라는 뜻이다.
- 키보드 내리기: `✓`, 박스 밖 탭, 끌기(일정 거리 이상), 두 손가락 핀치, Android
  뒤로가기. 끌기·핀치는 키보드를 내리며 그대로 `C-106-Arrange` 조작으로 이어진다.
- `C-106`에서는 캔버스 너비에서 자동 줄바꿈, `C-106-Arrange`에서는 줄바꿈 없이 핀치
  확대가 제한 없이 동작한다([[src-figma-주석-캔버스-C-SY]]).
- **공백·줄바꿈만 남으면 빈 내용이다.** 새 텍스트를 빈 채로 내리면 팝업 없이
  `C-001`로 간다.

## 저장 시점과 마감

- 키보드를 내려도 화면에만 반영된다. **서버 저장은 `[캔버스에 쌓기]`에서만** — 사진
  편집 세션과 같은 규칙이다([[topping-placement-pipeline]]).
- 헤더 `X` → 변경이 있으면 **`Modal-Quit-Add-Text`** 1회 → 전부 취소.
- **작성·편집 중 03:00 마감이 오면 업로드되지 않는다.** 원본은 "사진 업로드 중
  마감과 똑같이 처리"라 적는데, 기준으로 든 사진 쪽 규칙은 위키 어디에도 없다.
  가장 가까운 것은 서비스 공통 규칙의 **"마감 시점에 배치를 확정하지 않은 토핑은
  폐기"**다([[canvas]]).

**작성자 기기 기준으로 고정하자는 제안이 있다.** 기기마다 키보드 높이가 달라 같은
텍스트도 자동 크기가 달라질 수 있어, 개발 확인 목록이 **"작성자 기기에서 정한
크기·배율을 저장하고 보는 쪽은 다시 계산하지 않는다"**를 제안한다. 결정이 아니라
질문 목록이다(원본이 "클로드가 적어줬어요"라 밝혔다).

## 배치 보조 — 가이드와 자석 스냅

**텍스트 피드백에서 출발해 사진에도 붙었다.** 11-03의 "캔버스 배치 시 가운데
정렬, 수직/수평 확인"이 추진됐고 11-10에 완료됐다. 11-05 Figma 문서
[[src-토핑-중앙-정렬-및-각도-가이드-스냅-v0.1]]이 **이미지·텍스트 공통, 최초 배치와
수정 모두**로 정한다.

| 가이드 | 조건 | 결과 |
|---|---|---|
| 위치(옐로우 실선) | 토핑 중심이 캔버스 정중앙 세로선·가로선에서 **6pt** 안 | 가이드 + 그 축 0.5로 스냅 + 햅틱 1회 |
| 각도(민트 점선) | 회전이 **0°·90°·180°·270° ±3°** 안 | 가이드 + 그 각도로 스냅 + 햅틱 1회 |

손을 떼면 가이드가 사라지고 **스냅된 값으로 저장된다.** 6pt·±3°는 "빌드 확인 후
조정 가능"한 시작값이다. 텍스트 배치 화면에는 `Edit-Area`가 없다.

| 도착지 | `C-001` |
| 제목 / 본문 | `{그룹명} 파르페에 체리 하나 톡!` / **`{그룹 내 닉네임}: {미리보기}`** |
| 미리보기 | 줄바꿈·연속 공백을 공백 1개로, trim, **11자 이하면 그대로, 넘으면 앞 10자 + `…`.** grapheme 단위로 센다 |

**메신저 형식을 고른 이유가 적혔다** — "누가 말을 걸었다"로 읽히게 해 답장하러
들어오는 부담을 낮춘다. 스타일은 반영하지 않는다. 신규 등록만 트리거이고 수정·삭제는
보내지 않는다. 작성자가 나갔으면 닉네임 자리가 `누군가`다.

**`P-04`가 "화면 코드 미정"이라 적은 시점(10-07 `v0.2`)에 Figma는 이미 `C-106`을
텍스트 입력으로 쓰고 있었다**(10-13 카드). 푸시 정책서가 그것을 받아 적지 않았다.

삭제된 텍스트를 푸시로 열면 `해당 텍스트는 삭제됐어요` 토스트다([[toast]]).

## 미결

- **업로드 후 수정 가능 여부** — 회의 결정과 정책서 본문이 갈린다(위 상충 마커).
- **일본어·중국어 지원**이 회의록에서 결정되지 않았다. 정책서는 Line Seed JP/TW
  번들을 적지만 간체 지원 여부는 없다.
- **`P-04`의 트리거 화면**이 푸시 정책서에서 "미정"이다.
- **텍스트가 `G-001` 토핑 프레임에 어떻게 그려지는지** 없다.
- **"사진 업로드 중 마감" 규칙**이 어디에도 없다 — 텍스트 마감 규칙의 기준이 비어
  있다.
- **편집 중 남의 변경이 폴링으로 들어오면** 어떻게 하는지 없다(사진 편집도 같다).
