# 계정

## 정의

사람 한 명에 대응하는 앱 레벨 단위다. [[group]]이 그룹마다 따로 존재하는 것과
달리 계정은 하나뿐이고, 가입한 모든 그룹을 가로지른다.

소셜 로그인으로만 만들어지고 지울 수 있다. 자체 회원가입이 없다.

## 만들기

`A-002`에서 **카카오 또는 애플**로 로그인한다. 소셜 SDK가 토큰을 발급하면 서버가
사용자를 등록·조회하고 JWT를 돌려준다.

- **Apple은 잘라낼 수 없다** — iOS 정책상 필수다. 기능정의서가 근거를 밝힌 몇 안
  되는 항목이다([[mvp-scope-limits]]).
- 신규 사용자는 계정 이름을 소셜에서 받아오고, 없으면 **랜덤 부여**한다. 가입일을
  함께 저장한다. 부여 규칙은 아래 "초기 닉네임은 3000가지에서 나온다"에 있다.
- **프로필 이미지**는 아래를 본다 — 두 소스가 어긋난다.
- 약관에 동의하지 않으면 진입을 막는다. v5부터 약관 동의가 `A-003`으로 분리됐다.

## 계정이 갖는 것

`S-002`(계정 정보)에서 본다 — **닉네임**, 소셜 로그인 정보, 가입일.

## 프로필 이미지 — 두 읽기가 한 판본에서 만났다

v5(06-25)가 `A-002`에서 **"프로필 이미지 안넣음"**으로 확정했는데 컬러 규칙서
넷이 프로필 이미지를 정의해, **사용자가 올리는 사진**과 **자동 생성 이니셜 칩**이
서로 다른 것이라는 읽기가 성립하지만 **어느 문서도 그렇게 적지 않은** 상태가
두 판본 이어졌다.

**[[src-기능정의서-v7]]이 둘을 같은 문서에 실었다.**

| 행 | 무엇을 적나 |
|---|---|
| `A-002` 기타 | **"프로필 이미지 없음"** (그대로) |
| `S-002` 기타 | **`[프로필 이미지 정책]` 전문** — `Nametag-Chip` 12종 랜덤 배정, 계정 고정, 변경 기능 없음 |

**한 판본이 둘을 나란히 적었으므로 양립하는 읽기가 확인된다** — 올리는 사진은
없고, 이니셜 칩은 있다. 다만 **`A-002`의 "프로필 이미지"가 올리는 사진을
가리킨다고 명시한 문장은 여전히 없다.**

컬러 규칙서가 정하는 것은 **닉네임 첫 글자가 들어간 원형 이미지**
(`Nametag-Chip`)다. 6개 컬러 × 각 2개 타입 = **12종**이고 계정당 **1종을 랜덤
배정**한다.

**13번째 상태가 생겼다** — [[src-S-101-프로필-닉네임-컬러-규칙-v0.4]](08-17)의
**Default**다. 아래 "Default 상태"를 본다.

컬러 이름은 연핑크·진핑크·**체리**·그레이·**멜론**·**푸딩**이다 — 디저트 은유가
팔레트까지 내려왔다([[parfait]]).

칩 타입은 **텍스트 컬러 둘**로 이어진다 — 토스트 알림의 닉네임([[toast]])과
`G-001` 그룹 목록의 `Grouptag-Chip` Timestamp([[infinite-parfait]])다. 칩은 랜덤
배정이지만 거기서 파생되는 텍스트 컬러는 매핑으로 결정된다.

**두 매핑은 같은 타입을 읽되 표가 다르다.** Cherry 계열만 한 단계씩 어긋나고
(Timestamp 100/200/300, 토스트 닉네임 200/300/400) 그레이·멜론·푸딩은 같다.
[[src-S-101-프로필-이미지-및-그룹칩-내-타임스탬프-컬러-규칙-v0.1]]이 **"서로
다른 UI 요소용 별개 매핑이므로 상충이 아니다"**라고 직접 못박았다.

### 타입은 계정에 고정된다

타입은 **계정 생성 시 1회 랜덤 배정**되고 **이후 변하지 않는다.** 앱 재접속에도, 그룹을 옮겨도, 닉네임을 바꿔도 같다. 타입 변경 기능은
없다.

**타입이 닉네임이 아니라 계정에 묶인다.** 닉네임 `홍씨`인 계정 둘이 각각
`Type 1`과 `Type 8`을 받을 수 있다.

**그런데 칩이 12종이고 [[group]]의 최대 인원도 12명이다.** 배정이 계정 단위
랜덤이라 **그룹 안에서 타입이 겹치는 것을 막는 서술이 없다** — 12명이 12종을
무작위로 뽑아 전원 다를 확률은 0.006%에 못 미친다. 색으로 사람을 구분하려는
의도라면 거의 항상 겹친다.

## 닉네임은 두 층이다

[[src-S-002-앱닉네임-정책-v0.1]]이 처음 밝힌 구조다.

| | 어디에 | 무엇 |
|---|---|---|
| **앱 닉네임** | `S-002` · 계정 | 계정 하나에 하나 |
| **그룹 내 닉네임** | `S-102` · 그룹 | 가입한 그룹마다 따로 |

**입력 규칙은 둘이 같다.** 정책서도 계열이 둘인데
([[src-S-002-앱닉네임-정책-v0.2]], [[src-S-102-닉네임-정책-v0.2]]) **`v0.2` 쌍은
본문 1003자가 한 글자도 다르지 않다.** `v0.1` 쌍의 "본문 동일, 헤더만 다름"이
**두 판본 연속으로 반복됐다.**

**중복이 의도라는 것을 [[src-S-002-앱닉네임-정책-v0.2]]가 밝혔다** —
**"두 화면이 나중에 갈라질 수 있어 문서를 합치지 않고 계열을 유지한다."**
이 위키가 07-02의 세 문서를 보고 "화면 단위 관행"으로 추정했던 것의 실제 이유다.

**다만 그 문장이 한쪽에만 있고 둘의 적용 화면 서술이 어긋난다** —
`S-002` 쪽은 자기를 `S-002` 하나로 좁히고, `S-102` 쪽은 **두 화면을 모두
든다**([[open-questions]]).

| 항목 | 규칙 |
|---|---|
| 허용 문자 | 한글, 영문, 숫자, **공백**. 특수문자·이모지 불가 |
| 글자 수 | **1자 ~ 15자.** 글자 사이 공백도 1글자로 센다 |
| 공백 위치 | 맨 앞·맨 뒤 불가. 글자 사이는 1칸만, 연속 공백 불가 |

앱 닉네임에는 이 규칙이 **초기 자동 생성 닉네임을 수정하는 시점부터** 적용된다.

**그룹 내 닉네임에도 같은 규칙이 걸린다.**
[[src-S-002-앱-닉네임-생성-정책-v0.1]]이 장 번호로 못박았다 — 그룹 내 닉네임은
유효성 규칙만, 앱 닉네임은 **자동 생성이 먼저 걸리고 수정할 때부터** 유효성
규칙이다. **그룹 내 닉네임의 글자 수가 이로써 1~15자로 확정됐다**([[group]]).

**초기값은 두 층이 공유한다.**
[[src-S-102-그룹-닉네임-생성-정책-v0.1]]이 직접 적었다 — 계정 생성 시 **1회
만든 값 하나**가 **앱 닉네임과 최초 그룹 진입 시 그룹 내 닉네임에 공통으로**
쓰인다. **동일 로직·동일 결과값이고 계정 공통 1개를 재사용한다.** 그룹마다 다시
뽑지 않는다([[group]]).

**앞서 "자동 생성은 앱 닉네임 전용"으로 읽었던 것이 뒤집혔다** —
[[src-S-002-앱-닉네임-생성-정책-v0.1]] §4가 그룹 내 닉네임에 유효성 규칙만
들었을 뿐이고, 두 문서의 §4가 이 점에서 어긋난다([[open-questions]]).

**공유한 뒤가 없다.** 앱 닉네임을 고치면 이미 들어간 그룹의 닉네임도 따라
바뀌는지, 그때부터 독립인지 어느 문서도 말하지 않는다.

그룹명도 같은 구조의 규칙을 쓰지만 **상한이 10자**다
([[src-A-005-그룹명-정책-v0.1]]). 그 문서가 이 닉네임 정책서의 사본이라
구조가 같다.

**같은 규칙을 든 문서가 다섯이 됐다**(현행 넷) — `S-002` 계열 둘,
[[src-S-002-앱-닉네임-생성-정책-v0.1]], `S-102` 닉네임 정책서, 그룹명 정책서다.
**합치지 않는 이유는 밝혀졌으나 한쪽만 고쳐질 위험은 그대로다**
([[open-questions]]).

**중복과 금칙어가 v7에서 닫혔다.** v3까지 닉네임 정책의 항목 목록에 있다가
사라졌고([[spec-version-history]]), v6는 `S-102` 분기조건에 **"글자수/금칙어/
그룹 내 중복 정책 적용"**이라 적고도 그 정책을 어디에도 두지 않았다.

[[src-기능정의서-v7]]의 `S-102` 분기조건이 **"그룹 내 중복 허용(그룹원 12명 모두
같은 닉네임 가능), 금칙어 제한 없음"**이라 적는다 — **적용하라는 말이 실제 규칙이
됐다**([[group]]).

**다만 그룹 안쪽 이야기다.** `S-002` 앱 닉네임의 **계정 간 중복**은 v7도 다루지
않는다. 생성 정책서가 "계정당 유일성이 필요 없다면(중복 허용)"이라는 조건절로
한 번 스칠 뿐이다.

### 초기 닉네임은 3000가지에서 나온다

[[src-S-002-앱-닉네임-생성-정책-v0.1]]이 정한다. **계정 생성 시 1회**,
`형용사/동사` **100개**와 `파르페 재료` **30개**에서 하나씩 뽑아 **공백 없이
붙인다** — `녹는딸기`, `몽글한푸딩`, `스며드는블루베리`.

- **계정 생성 즉시 DB에 저장**하고 이후 재계산하지 않는다.
- 풀에 **중복 항목은 없고** 조합은 **3000가지**다.
- **생성 주체가 미정이다**(`[K2]`). 원본이 **어뷰징·치우침 방지 관점에서 서버
  생성을 권장**한다고 근거까지 적었다.

[[src-S-002-앱닉네임-정책-v0.2]](07-25)가 같은 규칙을 **요약으로** 싣되 단어
목록은 **"노션 참고"**로 밖을 가리킨다. 100개와 30개를 실제로 가진 소스는
[[src-S-002-앱-닉네임-생성-정책-v0.1]]뿐이라 그것이 가리켜진 문서로 읽히나,
**링크가 전사되지 않아 확인할 수 없다.** `[K2]`도 `v0.2`에는 없다
([[open-questions]]).

**재료 풀이 제품의 다른 어휘와 겹친다.** 프로필 칩 컬러 이름 **체리·멜론·푸딩**이
그대로 들어 있고 바닐라·초콜렛도 있다. 폐기된 빈 토핑 템플릿 6종 중
**딸기·키위·오레오**도 있다. **디저트 은유가 사람의 이름까지 내려왔다**
([[parfait]]).

## Default 상태

[[src-S-101-프로필-닉네임-컬러-규칙-v0.4]]가 더했다. **12종 타입 대신 Default
`Nametag-Chip`을 노출하는 상태**다.

- **탈퇴한 그룹원**의 칩을 노출해야 할 때
- 칩 **불러오기에 실패**했을 때
- **그 밖에 정상 결정할 수 없는 모든 상황** — 원문이 "Nametag-Chip에 문제 생기면
  다 Default로 노출해주시면 됩니다"라 적어 **앞의 둘이 닫힌 목록이 아님**을
  밝혔다

**표현은 컴포넌트마다 다르다.** 원문 서술이 아니라 예시 이미지에서 읽은 것이다.

| 컴포넌트 | Default 표현 |
|---|---|
| `Nametag-Chip` | 회색·흰 원형에 첫 글자 대신 **`-` 대시** |
| `Toast > Username` | **"알 수 없는 사용자가 59분 전에 쌓았어요"**([[toast]]) |
| `Grouptag-Chip` | 닉네임 자리에 **"알수없음"**([[infinite-parfait]]) |

**컬러 토큰 이름이 없다.** 이 문서의 나머지 여섯 상태는 전부 토큰으로 적혀
있는데(`Cherry-200`~`Pudding`) Default만 없다. 예시에서 회색 계열로만 확인된다
([[open-questions]]).

## 탈퇴와 로그아웃

- **서비스 탈퇴**(`S-003`) — 가입한 모든 그룹에서 자동으로 나가고 계정과 데이터를
  삭제한 뒤 앱을 종료한다. **soft delete**이며 재가입하면 **새 사용자로
  취급**한다. 데이터 보존·삭제 정책은 법적 검토 대기다.
- **로그아웃**(`S-005`) — **다섯 판본 만에 동작이 적혔다.** v2~v6는 "일단
  버튼만"이고 시스템 동작 열이 비어 있었는데, [[src-기능정의서-v7]]이
  **확인 모달 없이 즉시 처리 후 `A-002-1`(로그인)로 이동**한다고 적었다.
  전용 프레임이 없는 것도 **"확인 화면이 없으므로 디자인 누락이 아니다"**라고
  밝혔다.
- **푸시 토큰만 다르게 지운다.** 탈퇴·로그아웃 둘 다 **푸시 토큰은 soft delete
  대상이 아니라 즉시 하드 삭제**이고, 재로그인하면 다시 등록한다
  ([[push-notification]]). **이 위키에서 soft/hard delete를 구분한 첫
  서술이다.**

탈퇴한 사용자가 남긴 토핑은 지워지지 않는다. 작성자 표기가 '알 수 없음'이 된다
([[canvas]] `C-202`). **칩도 Default로 바뀐다**(위 절) — 이미지 주석이
**"탈퇴했으면 무조건 이름 알수없음임"**이다.

**표기가 셋으로 갈린다** — `알 수 없음`([[src-기능정의서-v6]] `C-202`),
`알 수 없는 사용자`([[src-C-202-토핑-편집자-확인-규칙-v0.1]]과 Toast 예시),
`알수없음`(`Grouptag-Chip` 예시). 컴포넌트마다 고정인지 **원본이 "예시로만
제시"라고 스스로 밝혔다**([[open-questions]]).

## 미결

- 그룹 가입 시 그룹 내 닉네임의 기본값이 무엇인지 — 앱 닉네임이 들어가는지.
- 자동 생성 조합 하나가 기능정의서의 "10자 이내"를 넘는다(위 상충 마커).
- 자동 생성 주체가 서버인지 클라이언트인지(`[K2]`).
- **앱 닉네임의 계정 간 중복.** 그룹 내 중복과 금칙어는 v7이 닫았다.
- 같은 규칙이 **네 정책서**에 중복으로 존재한다 — 한쪽만 고쳐질 위험.
- `v0.2`가 가리키는 노션 단어 목록 문서가 어느 것인지 링크가 없어 확인 불가.
- 두 생성 정책서의 §4가 그룹 내 닉네임의 자동 생성에서 어긋난다.
- 초기값을 공유한 뒤 두 층이 독립으로 움직이는지.
- **한 계정으로 여러 기기에 로그인할 수 있는지** — v5가 `S-002` 예외처리에 검토
  항목으로 붙였다.
- Default의 컬러 토큰 이름이 없다.
- Default 문구 표기가 셋으로 갈리고 컴포넌트마다 고정인지 없다.
- `A-002`의 "프로필 이미지 없음"이 **올리는 사진**을 가리킨다고 명시한 문장이
  없다. v7이 둘을 나란히 실어 읽기는 확인됐으나 서술은 여전히 없다.
- 그룹 안에서 칩 타입이 겹치는 것을 막지 않는다.
- 탈퇴 시 데이터 보존·삭제 정책(법적 검토 대기). **푸시 토큰 한 줄만 닫혔다.**
- **`A-006`의 "앱 닉네임 플레이스홀더"가 v1.0.1에서 동작하지 않는다**고 v7이
  스스로 적었다. 플레이스홀더가 초기값 공유와 같은 것인지도 없다.

전부 [[open-questions]]에 있다.
